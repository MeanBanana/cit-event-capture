## Schema

### Users and roles

Everyone who uses the app has one row in `"User"`. Citizens and investigators have one extra row in their own sub-table with the details only they have. Admins have no extra details, so they only have a `"User"` row.

```text
auth.users  (Supabase Auth: email, hashed password, login sessions)
    │  authid
    ▼
"User"  (everyone: username, name, email, phone, role)
    ├──► citizen       (only when role = 'citizen')
    └──► investigator  (only when role = 'investigator')
```

**`"User"`** — note the capital U: the name must be written with quotes in SQL (`public."User"`), but in Flutter it is simply `.from('User')`.

| Column | Type | Notes |
|---|---|---|
| `userid` | integer, PK | Referenced by every other table (reportedby, uploadedby, assignedto…) |
| `authid` | uuid, unique, not null | Link to `auth.users.id`. Meant to be set to empty if the login is deleted, so the evidence trail is kept; but `20261006081759_remote_schema.sql` made it `NOT NULL`, so deleting a login that has a profile currently fails (see [Still to do](#still-to-do)) |
| `username` | varchar(30) | Used to log in. Unique ignoring case. Letters, numbers, `_` and `.`, 3–30 characters |
| `firstname` | varchar(100) | |
| `surname` | varchar(100) | |
| `email` | varchar(150), unique | Copied from Supabase Auth and kept in sync automatically |
| `phonenumber` | varchar(20) | Optional |
| `role` | `user_role` enum | `citizen`, `investigator` or `admin` |
| `datecreated` | timestamptz | Set automatically |

**`citizen`**

| Column | Type | Notes |
|---|---|---|
| `userid` | integer, PK | Points to `"User"` |
| `role` | `user_role` | Always `citizen` (this is what stops a non-citizen having a citizen row) |
| `residence` | text | The registration screen should make this required |

**`investigator`**

| Column | Type | Notes |
|---|---|---|
| `userid` | integer, PK | Points to `"User"` |
| `role` | `user_role` | Always `investigator` |
| `rank` | varchar(50) | e.g. `Sgt.` |
| `badgenumber` | varchar(50), unique | e.g. `JHB-4471` |
| `station` | varchar(150) | e.g. `Kempton Park SAPS` |
| `unit` | varchar(100) | e.g. `CIT Task Force` |
| `dutystatus` | varchar(20) | `on_duty`, `available` (default) or `off_duty` |

The sub-tables point at `"User"` using **both** `userid` and `role`. Because of this the database guarantees that a citizen row only belongs to a citizen and an investigator row only to an investigator. To change someone's role, first delete their row from the old sub-table.

### Investigation tables

| Table | Holds | Links to |
|---|---|---|
| `cases` | One investigation, created by an admin: title, description, status (`open`, `under_review`, `closed`), date created, date closed (set automatically when status becomes `closed`) | `createdby` → User |
| `crimescene` | A reported incident (a "submission"): location, date/time, attack type, status (`open`, `closed`, `under_review`), description (the citizen's own words). `datereported` is when it was reported (set by the database; `datetime` is when it happened). `latitude`/`longitude` come from the phone's GPS (both or neither). `locationkey` is the location in a standard form (`"N1, Midrand"` → `n1 midrand`, generated by the database) used to group by location. `caseid` is empty until an admin adds the incident to a case. `reviewstatus` is the admin's decision: `pending`, `accepted` (in a case), `rejected` (kept on record, with `reviewnote`) or `duplicate` (of `duplicateof`, follows it into its case); `reviewedby`/`reviewedat` record who decided and when. The database refuses any row where these don't match. `aisummary` / `aisummarystatus` / `aisummaryat`: the AI's short summary of all the incident's footage (see [The AI pipeline](#the-ai-pipeline-what-it-writes)) | `reportedby` → User, `caseid` → cases |
| `media` | Footage/photos uploaded to an incident: type (`image`, `video`, `audio`), storage path, file hash/size, timestamps, processing status (`pending`, `processing`, `completed`, `failed`). `aidescription` / `aidescribedat`: what the AI saw in this one clip | `incidentid` → crimescene, `uploadedby` → User |
| `detection` | What the AI found in a media file: type (`vehicle`, `person`, `weapon`), frame time, bounding box, confidence, model version. `verified` / `verifiedby` / `verifiedat`: an investigator on the case (or an admin) confirmed it, so AI-suggested results can be told apart from confirmed ones. **Person detections only:** `suspectstatus` is `possible` (not reviewed yet, the start for every person), `confirmed` (an investigator confirmed them as a suspect; a `suspect` row exists) or `dismissed` (not a suspect, e.g. a guard; `suspectreviewnote` must say why), with `suspectreviewedby` / `suspectreviewedat`. Only the review functions can change these (see [Suspects and POPIA](#suspects-and-popia)) | `mediaid` → media, `verifiedby` / `suspectreviewedby` → User |
| `vehicledetail` | Vehicle details for a vehicle detection: make, model, colour, number plate, plate confidence | `detectionid` → detection (one-to-one) |
| `weapondetail` | Weapon details for a weapon detection: type (`handgun`, `rifle`, `shotgun`, `knife`, `explosive`, `other`, `unknown`), description, and optionally the suspect carrying it (must be from the same incident) | `detectionid` → detection (one-to-one), `suspectid` → suspect |
| `suspect` | A person detection that an **investigator assigned to the case** has confirmed as a suspect: physical and clothing description (weapons are in `weapondetail`). Must be a `person` detection from the same incident. Written only by `review_possible_suspect` / `update_suspect_details`; removed again by `undo_suspect_review` | `detectionid` → detection, `incidentid` → crimescene, `confirmedby` → User |
| `correctionlog` | Audit trail of corrections to AI results (original and corrected value) | `detectionid` → detection, `correctedby` → User |
| `caseassignment` | Which investigator is assigned to which case, by whom, and the status (`active`, `reassigned`, `closed`). An investigator can have only one `active` assignment per case. `islead` marks the lead investigator: at most one active lead per case, and the first investigator assigned becomes lead | `caseid` → cases, `assignedto` / `assignedby` → User |
| `crossreferencelink` | Links the same vehicle or suspect across different incidents, with match confidence and verification status. For `vehicle` links `entityid_a`/`entityid_b` are `vehicledetail.vehicledetectionid`; for `suspect` links they are `suspect.suspectid`. Used for the Linked view and the case suggestions (`rejected` links are ignored) | `linkedby` → User |
| `caseevent` | The history of every submission and case: submitted, added to / removed from a case, rejected, duplicate, reopened, case created / edited / status changed / deleted, investigator assigned / removed, lead changed, detection verified, suspect confirmed / dismissed / review undone / edited (with the reason; descriptions themselves are not copied in). Written **only by triggers**, so it is complete whichever screen or function made the change; nobody can edit or delete it from the app | `caseid` → cases, `incidentid` → crimescene, `actor` → User |

See `diagrams/ERD.png` for the diagram (it still needs updating to show the `citizen` and `investigator` tables).

## Accounts, login and passwords

### Passwords are handled by Supabase Auth

Our tables never store passwords or login tokens. Supabase Auth keeps them in its own `auth.users` table (you can see accounts under **Dashboard → Authentication → Users**).

* The app sends the email and password straight to Supabase Auth (`signUp` / `signInWithPassword`).
* Supabase stores only a one-way hash of the password and checks it at login.
* On a successful login Supabase gives the app a session token (JWT). The Flutter SDK stores it, sends it with every request and refreshes it automatically.
* The database reads the token to know who is asking (`auth.uid()`), matches it to `"User".authid`, and the RLS policies decide what that person may see.

### How each type of account is created

| Account | How it is created | What the database does |
|---|---|---|
| **Citizen** | Registers in the app with `supabase.auth.signUp(...)`, sending `username`, `firstname`, `surname`, `phonenumber`, `residence` as sign-up data | The `on_auth_user_created` trigger creates the `"User"` row and the `citizen` row. **App sign-ups are always citizens** — a role sent from the app is ignored |
| **Investigator** | An admin taps **+ New investigator** on the Investigators tab and fills in the popup, which calls the `create-investigator` Edge Function (see [Creating investigator accounts](#creating-investigator-accounts)) | The Edge Function creates the login with the service key and puts `role: investigator` in `app_metadata`, which only the service key can set. The trigger then creates the `"User"` and `investigator` rows. The investigator then sets their own password through the same reset link as **Forgot password?** (see below) |
| **Admin** | Manually, by the database owner (see below) | — |

**Creating an admin** (one-time, by the database owner):

1. **Dashboard → Authentication → Users → Add user** (email + password). The trigger creates them as a citizen.
2. In the **SQL editor**:
   ```sql
   DELETE FROM public.citizen
     WHERE userid = (SELECT userid FROM public."User" WHERE email = 'person@example.com');
   UPDATE public."User"
     SET role = 'admin', username = 'TheirUsername', firstname = 'First', surname = 'Last'
     WHERE email = 'person@example.com';
   ```
   The `DELETE` must run first — the database will not change the role while a citizen row exists.

### Creating investigator accounts

`functions/create-investigator/index.ts` runs on Supabase's servers, so the service key never goes into the app:

1. It reads the caller's login token and checks their `"User".role` is `admin` (anyone else gets "Only a system administrator can add investigators.").
2. It checks the form (same rules as the app), then that the username (`username_available`) and badge number are free.
3. `auth.admin.createUser` with `email_confirm: true`, `app_metadata: { role: "investigator" }` and the form fields in `user_metadata` (`username`, `firstname`, `surname`, `phonenumber`, `rank`, `badgenumber`, `station`, `unit`). The `on_auth_user_created` trigger makes the `"User"` and `investigator` rows.
4. It returns `{ userid, email }`. Errors come back as `{ error: "message" }`, which the app shows as they are.

The account has **no password**. The investigator opens the app on their own phone, taps **Forgot password?** and enters their email. (The function does not send the reset email itself, because reset links only open on the phone that asked for them.)

**Deploy** (once, and after every change to the function), from the `database/` folder:

```bash
supabase login                      # first time only
supabase link --project-ref tnydrlxptqegzhbvwpcq   # first time only
supabase functions deploy create-investigator
```

`config.toml` sets `verify_jwt = false` for this function because it checks the caller itself (step 1). `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are provided to Edge Functions automatically; nothing needs to be added by hand. Until it is deployed, the app shows "This feature is not set up on the server yet." Logs: **Dashboard → Edge Functions → create-investigator → Logs**.

### Logging in with a username

Supabase Auth logs in with an **email**, but our login screen asks for a **username**. The app first calls `email_for_username` to look up the email, then logs in with it. Trade-off: anyone who knows a username can find that user's email. If the team decides that is a problem, change the login field to Email and remove the function.

### Setting and resetting passwords

Anyone who taps **Forgot password?** on the login page gets an email with a **reset link**. Tapping the link on the phone opens the app on a "New Password" screen:

1. The app calls `resetPasswordForEmail(email, redirectTo: 'argusshield://reset-password')`. Supabase answers the same way whether or not the email has an account, so nobody can use it to find out which emails are registered.
2. The link in the email opens the app (Android intent filter in `AndroidManifest.xml`, iOS URL scheme in `Info.plist`). `supabase_flutter` checks the link with Supabase, signs the user in for this one purpose and fires `AuthChangeEvent.passwordRecovery`.
3. `main.dart` hears that event and opens `ResetPasswordPage`. The user types the new password twice, the app calls `updateUser(UserAttributes(password: ...))`, signs out and goes back to the login page.

Things to know:

* The link only works **on the phone that asked for it** (the app uses the PKCE flow, which keeps a secret on that phone). Opening it on a computer does nothing.
* An old or already-used link shows "This reset link is invalid or has expired".
* Supabase allows one reset email per account per minute.

This needs, in the Supabase dashboard:

* **Authentication → URL Configuration → Redirect URLs** must include `argusshield://reset-password`. Without it Supabase ignores the redirect and the link opens the Site URL in a browser instead of the app.
* The **Reset Password** email template (Authentication → Emails) keeps the default `{{ .ConfirmationURL }}` link.
* The **Email** provider (Authentication → Sign In / Providers) must stay enabled. "Confirm email" can be on or off; it does not affect resets.
* A **custom SMTP provider** before real users rely on it (Authentication → Emails → SMTP Settings). Without one, Supabase's built-in email only sends to the project team's own addresses, a few per hour. That is enough for testing with your own account.

## Who can see and do what (RLS)

Every table has row-level security (RLS) enabled. The app uses the **publishable (anon) key** plus the logged-in user's token, so each query automatically returns only the rows that user may see — the app does not need to filter by user itself.

| Table | Citizen | Investigator | Admin |
|---|---|---|---|
| `"User"` | Own row; may edit own username, name, phone | Own row and other investigators | All; may change roles |
| `citizen` | Own row; may edit residence | — | All |
| `investigator` | — | All investigators; may change **only** own `dutystatus` | All; may edit everything |
| `cases` | — | See cases they are **actively assigned** to | Create, edit, close, delete |
| `crimescene` | Report incidents as themselves; see those they reported | See and update incidents in cases they are **actively assigned** to | All; only admins can review (`reviewstatus`, `caseid`, `duplicateof` ...) |
| `media` | Upload to incidents they reported; see own uploads | See and upload to assigned cases | All |
| `detection` | — | Assigned cases (read-only) | All (read) |
| `vehicledetail` | — | Assigned cases; may correct details | All |
| `weapondetail` | — | Assigned cases; may correct details | All |
| `suspect` | — | Assigned cases; confirm / dismiss possible suspects and edit descriptions, **only** through the review functions | Read only; may **undo** a review (with a reason), never confirm |
| `correctionlog` | — | Assigned cases; add corrections as themselves (no edits/deletes) | All; add corrections |
| `caseassignment` | — | Own assignments | Assign, reassign, close |
| `crossreferencelink` | — | View, create, update | All, incl. delete |
| `caseevent` | — | History of cases they are **actively assigned** to (read-only) | All (read-only) |

* **AI fields** (`crimescene.aisummary`, `aisummarystatus`, `aisummaryat`, `media.aidescription`, `aidescribedat`) can only be written with the service key: a trigger refuses them from the app.
* **Case status:** admins may set any status; an investigator assigned to the case may only move it between `open` and `under_review` (through `set_case_status`).
* **Suspects:** only an investigator actively assigned to the case can confirm or dismiss a possible suspect. Neither admins nor the AI pipeline can. See [Suspects and POPIA](#suspects-and-popia).
* **Not logged in:** no access to any table. Only `email_for_username` and `username_available` can be called.
* **Nobody** (through the app) can insert or delete `"User"`, `citizen` or `investigator` rows — only the sign-up trigger creates them.
* The **Python AI/CV pipeline** uses the **service role (secret) key**, which bypasses RLS, to write `detection`/`vehicledetail` rows and update `media.processingstatus`. That key must **never** be in the Flutter app or on GitHub.

## Suspects and POPIA

Under POPIA a person seen in footage is not treated as a suspect until a person responsible for the case has looked at them. So:

1. Every `person` detection the AI writes starts as a **possible suspect** (`detection.suspectstatus = 'possible'`). The pipeline cannot set anything else.
2. Only an **investigator actively assigned to the case** (not on a closed case) decides, with `review_possible_suspect`:
   * **confirm**: a `suspect` row is created with the investigator as `confirmedby`, optionally with physical / clothing descriptions and a note;
   * **dismiss**: not a suspect (bystander, guard, victim); a reason is required.
3. Investigators on the case can edit a confirmed suspect's descriptions (`update_suspect_details`).
4. The admin, or an investigator on the case, can **undo** a review with a reason (`undo_suspect_review`). The person goes back to `possible`; a confirmed suspect's record (and its descriptions) is deleted, weapons stop pointing at it and AI links to it are rejected. Admins cannot confirm anyone.
5. Every decision is written to `caseevent` by a trigger: who, when, what and why. Descriptions are not copied into the history.
6. The app shows **counts only** until someone is confirmed: `list_submissions` and `list_cases` return `possiblesuspects` and `confirmedsuspects`, each the most seen at once in one clip. For a case it is the highest of its submissions (A = 2, B = 1, C = 1 → "about 2"), since the same people usually appear in several reports.

The investigator screens that use these functions are not built yet (see [Still to do](#still-to-do)); until then everything stays `possible` unless an investigator account calls the functions directly.

## How a submission becomes a case

**The rule: a citizen submits, the AI analyses, the admin decides.** Nothing is added to a case without an admin accepting it, and investigators only see submissions that are in a case they are assigned to.

```text
citizen reports an incident           crimescene row, reviewstatus = 'pending'
  + uploads footage                   media rows (capture time from the file's metadata)
        │
        ▼
AI pipeline (service key)             detections, plates, per-clip descriptions,
                                      combined summary, cross-reference links
        │
        ▼
admin reviews (Submissions tab)       suggestions scored by match_incidents
   ├─ accept → new or existing case   attach_incident / create_case / add_incidents_to_case
   ├─ one tap: "Suggested matches"    list_suggested_matches → accept_suggested_matches
   ├─ reject (kept on record)         reject_submission
   └─ duplicate of another            mark_duplicate
        │
        ▼
case: investigators assigned (first one is lead), status open → under review → closed
every step above is written to caseevent (the case history)
```

**When did it happen?** `incident_time()` uses the earliest capture time in the footage's metadata (`media.capturetimestamp`) and falls back to the time the citizen typed. When the two disagree by more than 3 hours, `list_submissions` sets `timemismatch` and the app shows a warning.

**Suggestions** compare a submission with the submissions already in open cases (`match_incidents`):

| Signal | Points |
|---|---|
| AI cross-reference link | verified +50, pending +35 |
| Same number plate | +40 (one character apart, an OCR misread: +25) |
| Within 5 km (GPS) | +30 (no GPS but same location text: +20) |
| Within 2 hours | +30 (within 24 hours: +10) |
| Same vehicle colour + make | +10 |

Under 30 is not shown. 30–59 is a "possible match" (case page recommendations only), 60–89 "likely" and 90+ "strong" (also in the Suggested matches review list). The reasons ("Same plate ND123456GP", "750 m apart", "40 min apart (video time)") are shown to the admin, so a suggestion can always be explained.

**Removing a submission from a case never deletes it**: `reopen_submission` puts it back to `pending` with all its footage and history.

With `p_search`, only those whose badge number or name contains it (any case). Normal RLS applies, so citizens get nothing |
| `admin_overview_stats()` | callable by logged-in users | One row for the admin Overview tiles: `totalcases`, `activecases` (open/under review), `pendingcases` (submissions waiting for review), `investigators`. Normal RLS applies, so only admins get the full totals |
| `list_submissions(p_search, p_limit, p_review, p_caseid, p_order, p_after_time, p_after_id, p_locationkey, p_ids)` | callable by logged-in users | One page of incidents (default 30, max 100), `newest` or `oldest` reported first, with reporter name, media count, case title, review details, GPS, the AI summary and what the AI saw (`vehiclecount`, `personcount`, `weaponcount` = the most in any one clip; `plates` = up to 3 plates read; `capturedat` = earliest capture time in the footage; `timemismatch` = capture time and typed time more than 3 hours apart; `possiblesuspects` / `confirmedsuspects` = the most unreviewed / confirmed people in any one clip). **Paging:** pass the `datereported` and `incidentid` of the last row you have as `p_after_time` / `p_after_id` to get the next page — every page is an index range scan, so page 100 is as fast as page 1. Normal RLS applies (admins see all, citizens their own, investigators their assigned cases) |
| `list_incident_media(p_incidentid)` | callable by logged-in users | A submission's clips/photos with the AI's description of each and how many detections were found / verified |
| `list_location_groups(p_search, p_review, p_limit, p_offset)` | callable by logged-in users | Submissions grouped by `locationkey`, most recently reported first, with the most common spelling as the label and the pending count |
| `list_linked_groups(p_limit, p_offset)` | callable by logged-in users | Groups of submissions joined by `crossreferencelink` (A–B and B–C puts A, B and C together), groups with something pending first, with link counts, best confidence and plates seen in 2+ of them |
| `incident_links()` | helper | Every non-rejected cross-reference link as a pair of incident ids |
| `match_incidents(p_candidates, p_targets)` | helper | Scores every candidate/target pair: verified AI link +50 (pending +35), same plate +40 (or plates one character apart +25, an OCR misread), within 5 km +30 (or same location text +20), within 2 h +30 (or 24 h +10) using `incident_time`, same vehicle colour + make +10. Pairs under 30 are left out. Returns the score and readable reasons ("Same plate ND123456GP", "750 m apart", "40 min apart (video time)") |
| `incident_time(p_incidentid)` | helper | When it happened: the earliest `media.capturetimestamp` (footage metadata), otherwise the time the citizen typed |

| `suggest_incidents_for_case(p_caseid, p_limit)` | admin action | Pending submissions that probably belong in the case, best first (only those within 14 days of the case's incidents, or linked / sharing a plate, are compared) |
| `suggest_cases_for_incident(p_incidentid, p_limit)` | admin action | Open / under-review cases a submission probably belongs to, best first |
| `list_suggested_matches(p_minscore, p_limit)` | admin action | Pending submissions (last 30 days) that most likely belong to an existing open case (score ≥ 60), each with its best case, the reasons and how many other cases also match. Feeds the "Suggested matches" review list |
| `accept_suggested_matches(p_incidentids, p_caseids)` | admin action | Adds the matches the admin ticked (`p_incidentids[i]` into `p_caseids[i]`) in one transaction; ones already reviewed or whose case was closed are skipped. ### Keys

Found under **Dashboard → Project Settings → API Keys**.

|---|---|
| Project URL | Flutter app |

```dart
await Supabase.initialize(
  url: 'https://<project-ref>.supabase.co',
  publishableKey: 'sb_publishable_...',   // as in mobile/argus_shield/lib/main.dart
);
final supabase = Supabase.instance.client;
```

### Registration (citizen)

```dart
final free = await supabase.rpc('username_available',
    params: {'p_username': username}) as bool;
if (!free) throw 'That username is taken';

final res = await supabase.auth.signUp(
  email: email,
  password: password,
  data: {
    'username': username,
    'firstname': firstname,
    'surname': surname,
    'phonenumber': phone,
    'residence': residence,
  },
);
// With "Confirm email" on, a duplicate email returns a user with no identities instead of an error
if (res.user != null && (res.user!.identities?.isEmpty ?? true)) {
  throw 'An account with this email already exists';
}
```

### Login and role

```dart
final email = await supabase.rpc('email_for_username',
    params: {'p_username': username}) as String?;
if (email == null) throw 'Invalid username or password';   // same message either way
await supabase.auth.signInWithPassword(email: email, password: password);

final profile = await supabase
    .from('User')
    .select('userid, username, firstname, surname, role')
    .eq('authid', supabase.auth.currentUser!.id)
    .single();
// profile['role'] -> 'citizen' | 'investigator' | 'admin'  → choose the dashboard

// Extra details for a citizen or investigator:
final details = await supabase
    .from(profile['role'] == 'investigator' ? 'investigator' : 'citizen')
    .select()
    .eq('userid', profile['userid'])
    .single();
```

### Submissions, cases and suggestions (admin)

The app's calls are all in `mobile/argus_shield/lib/supabase_service.dart`. The pattern:

```dart
// One page (30) of submissions, newest first. For the next page, pass the
// datereported + incidentid of the last row you have: no row limit, and
// page 100 is as fast as page 1.
final page = await supabase.rpc('list_submissions', params: {
  'p_review': 'pending',            // optional filter
  'p_order': 'newest',              // or 'oldest'
  'p_after_time': last?.datereported,
  'p_after_id': last?.incidentid,
});

// Grouped views
await supabase.rpc('list_location_groups');
await supabase.rpc('list_linked_groups');

// The best suggestion + plate for a page of case cards

  'p_caseids': [3, 4, 7],

  'p_caseids':     [ 3,  3],
});
```

### Errors to handle

| Situation | What Flutter receives |
|---|---|
| Wrong username or password | `AuthException` (invalid login credentials) |
| Weak password | `AuthWeakPasswordException` |
| Email already registered, "Confirm email" **off** | `AuthException` with code `user_already_exists` |
| Email already registered, "Confirm email" **on** | No error — check `identities` as shown above |
| Username taken / invalid (if not checked first) | `AuthException` "Database error saving new user" — always call `username_available` first |
| A query the user is not allowed to run | An empty list (RLS hides the rows) or a `PostgrestException` |

## Workflow: making a database change

All Supabase commands run from `database/`. Git commands run from the repository root. Docker Desktop must be running.

### First-time setup

```bash
cd database
supabase login
supabase link --project-ref <project-ref>   # ask Carel for the project ref and database password
supabase migration list                     # every migration should show under both Local and Remote
```

### Step by step

1. **Branch** (from the repository root):
   ```bash
   git checkout main
   git pull
   git checkout -b database/short-description
   ```
2. **Check that GitHub and Supabase match** (from `database/`):
   ```bash
   supabase migration list    # Local and Remote columns must be identical
   supabase db pull           # should say "No schema changes found"
   ```
   If `db pull` writes a new file, someone changed the dashboard by hand. Read the file before continuing (see [Troubleshooting](#troubleshooting) for a known false alarm).
3. **Create the migration:**
   ```bash
   supabase migration new short_description
   ```
   Write the SQL in the new file under `supabase/migrations/`.
4. **(Optional) Test locally** on a throwaway database built from all migrations:
   ```bash
   supabase start
   supabase db reset
   supabase stop
   ```
5. **Dry run, then push** to Supabase Cloud:
   ```bash
   supabase db push --dry-run   # must list ONLY your new migration
   supabase db push
   supabase migration list      # your migration now shows under Local and Remote
   ```
6. **Commit and open a Pull Request** (from the repository root):
   ```bash
   git add database/supabase/migrations/
   git commit -m "Describe the database change"
   git push -u origin database/short-description
   ```

### Rules

* **Never** change tables, columns, policies or functions in the Supabase dashboard. Every change is a migration.
* **Never** edit a migration that has already been pushed — write a new one.
* A new table gets RLS turned on automatically but has **no policies**, so the app can't read it until policies are added in a migration.
* Changing data (e.g. creating the first admin) in the SQL editor is fine. Changing **structure** is not.

## Testing

Test every database change by checking what each role can and cannot see.

**In the app:** log in as a citizen, an investigator and an admin, and confirm each sees only what the [RLS table](#who-can-see-and-do-what-rls) says.

**In the SQL editor**, you can pretend to be a user. Everything inside the transaction is undone at the end:

```sql
BEGIN;
-- 1. pick the user (must come before SET ROLE: logged-in users can't read auth.users)
SELECT set_config('request.jwt.claims',
  json_build_object('sub', (SELECT id FROM auth.users WHERE email = 'someone@example.com'),
                    'role', 'authenticated')::text, true);
-- 2. act as a logged-in user
SET LOCAL ROLE authenticated;

SELECT * FROM public."User";         -- what can this person see?
SELECT * FROM public.investigator;

ROLLBACK;
```

## The AI pipeline: what it writes

The AI worker (GPU laptop / server, **service role key**) takes jobs from the
`aijob` queue and writes its results through database functions, one
transaction per save: one `detection` row per tracked person / vehicle / weapon
(with `vehicledetail` / `weapondetail`), the files' capture time and GPS, the
submission summary, and per case the combined people / vehicles / weapons
(`caseentity`) with the case summary. Person detections are always **possible
suspects** only; the AI never writes `suspect` rows (see
[Suspects and POPIA](#suspects-and-popia)).

Everything — the job kinds, the worker loop, which function does what, who may
call it, the tests and how it differs from `SUPABASE_AI_PIPELINE.md` — is in
**[AI_PIPELINE.md](AI_PIPELINE.md)**.

## Troubleshooting

**`Bind for 0.0.0.0:54320 failed: port is already allocated`** (during `db pull`)
A temporary database from an earlier run is still running in Docker. In PowerShell:
```powershell
docker ps -a --filter "publish=54320" --format "table {{.ID}}\t{{.Names}}\t{{.Status}}"
docker rm -f <the ID shown>
docker container prune -f
```

**`ports are not available ... 54320`** (Windows has reserved the port)
In an Administrator PowerShell: `net stop winnat` then `net start winnat`. Check reserved ranges with `netsh interface ipv4 show excludedportrange protocol=tcp`.

**`db pull` creates a file that only drops and re-adds the same CHECK constraints**
This is a false alarm from the Supabase CLI — nothing actually changed. Answer **No** to "Update remote migration history table?", delete the file (`Remove-Item supabase\migrations\<file>.sql`) and check `supabase migration list` shows only the real migrations.

**`Database error saving new user`** when signing up
The sign-up trigger rejected the data: usually a username that is taken or has invalid characters, or an investigator created without a badge number or station.

**Docker errors**
Make sure Docker Desktop is running and `docker info` works before any `supabase` command.
